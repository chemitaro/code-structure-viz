失敗時の「指紋なし」を、manifestでどう表すか

Next.js解析の公開契約を整える途中で、未認定の解析結果を正しく表す仕様と、全体manifestの必須項目に不整合が見つかりました。何が完成済みか、何が不足しているか、どの変更を判断する必要があるかを説明します。

第一候補は、Next枝に限定して現v2のroot指紋にnullを認める案です。ただし、外部・永続利用者へ現v2不変を保証していないことと、利用者を同時切替できることが条件です。保証がある場合は新root世代へ分離します。

この資料は提案です。新仕様の採択、コードレビュー合格、実装完了を意味しません。

2. 「指紋」は何を示す値か

fingerprintは、決められた入力をcanonical JSONにしてSHA-256で識別する値です。ただし、何を入力にするかによって意味が変わります。同じ64文字のdigestでも、別の指紋を代入してよいわけではありません。

値識別するもの証明しないこと
source fingerprint同じSourceView／sealが読んだ入力集合Node実行や解析成功
Nextのsemantic run fingerprint同じrequestとmatching transport／Coreの14-key familycomplete成功。Core rejectedでもnonnullになり得ます
既存generic run-fingerprint/v1Python／SQLAlchemyのsource・request・config等の七keyNextの14-key familyとの同一性
publication seal／measurement digest最終公開recordと実bytes／計測の整合性semantic admissionやcompiler使用成功

transportは、同じrequestに対応する応答を検証する境界です。Coreは、その応答をsourceや意味モデルへ照合し、受理または拒否する検証部です。これらのmatching ownerが無い場合、Nextのsemantic指紋はnullが正しいと現行仕様が定めています。

正本の14キーを確認する 
source_view_fingerprint, source_plan_digest, domain_config_digest,
projects, targets, formats, stdout_selector, limits,
node_version, typescript_version, adapter_version, protocol,
trusted_environment_digest, semantic_admission_profile_id

typescript_version=5.9.2はlocked expected metadataです。実際にcompilerをimport／useした独立証明ではありません。PID、host path、capture、結果count、response bodyを新たにhashへ加えません。

3. 不整合はどこにあるか

起動準備で失敗した場合、解析結果は未認定でも、失敗の説明自体は公開できます。現行domainは指紋nullを認めます。snapshot requestは指紋fieldの省略を認めます。一方、全体を束ねるroot manifestは指紋を必須stringとしています。

編集可能なPlantUMLソース

      
限定probeでは、実stage_failed request／runtime／run／candidatesから旧同値joinのrun blockだけを作ると、root schemaは指紋のNoneだけをstring違反として拒否しました。新root実装全体が壊れているというテストではありません。rootを実装する前に露呈した契約差分です。

4. nullは「失敗一般」でも「0 byte」でもない

      

        
具体例capturesemantic指紋解釈

        
          
起動準備stage_failednull／nullnull両captureも解析familyも未観測です。失敗説明は公開可能です。

captureとsemanticの意味は別ですが、任意の組合せを許すわけではありません。Current success／Coreをcapture未観測へ結ぶ正例は、下位ownerの不変条件に反するため作りません。

      
最終stderrやcaptureがoverflowした場合は、解析の成否とは別にpublication自体がfailureとなります。元runの指紋を保持し、公開responseはnull、artifactsは空にします。

    


    

      
5. 指紋だけ直しても、親設定の証拠が残る

      
rootは「設定値」と「その値をどこから選んだか」の両方を求めます。たとえば同じdepth=1でも、builtin defaultで選ばれた場合とCLIで指定された場合は違います。値だけを見て由来を復元できません。

      
Current RetainedNextAnalysisContextV2はresolved intent、run context、domain config、source seal／assetsを保持します。しかし、rootの七field value_sourcesすべての選択元を受け取る入力はありません。sealのconfig_resolutionはTypeScript設定の宣言元で、CLI設定の選択元とは別です。

      
config.sourceはbuiltin／repository／explicitです。各value_sourcesにはcliもあります。goldenのbuiltin metadataを新ownerの観測としてコピーしたり、budget_sourceだけを全limitsの由来へ広げたりしません。

      
採択後のDesignで、親設定解決時に値とoriginを一緒に保持するbounded reference ownerとsame request／contextへのjoinを具体化します。下位runtime／Core／run／candidatesのhashや意味は変えず、final ownerの追加input責務を仕様レビューへ含めます。製品CLIの実観測認定とは区別します。

    


    

      
6. 選択肢と第一候補

      

        
案利点負担・条件

        
          
A：現v2のNext枝限定nullable訂正14-keyの意味・正常digestを維持し、新hash／field／URNを増やしません。pre-productionの小さい訂正に向きます。旧nonnull validatorはnullを拒否します。外部不変保証が無く、schema／producer／validator／利用者を同時切替できることが条件です。非Next枝はnonnullを維持します。

          
B：新root世代旧contractとconsumerの不変保証を保ち、新nullを版で識別できます。schema／URN／dispatcher／reader／vectorsの最小affected closureが増えます。既存保存物を新意味へ読み替えません。

          
C：generic request指紋へ分離Core前でもnonnull入力identityが必要なら合理的です。新preimage、origin owner、consumer joinの意味を採択する必要があります。今回は最小修正を超えます。

          
D：manifest抑止、失敗専用hash、ゼロdigest表面上のschema違反を避けられます。通常failure公開やsemantic nullの正直な表現を壊すため不採用です。

        
      

      
Aを第一候補にする理由：Current root ownerは未実装で、新参照契約の認定前です。意味の不足は指紋nullを正直に投影すれば解消でき、新しい入力identityを作る必要はありません。外部consumerの不変義務があるなら、この小ささより互換性を優先してBを選びます。

      
ローカルのidentity文字列censusではschema、tests、Issue artifactsにhitし、src／docsのproduction v2 writerは見つかりませんでした。ただし動的loader、過去配布物、repository外利用者の完全調査ではありません。sdistはschemas／docsを含むため、外部利用者無しとは断定していません。

      
ここで確認したいのは「rootにも現v2の限定訂正を適用するか、新世代へ分離するか」です。すでに採択済みのadapter capture二field訂正を、別のroot変更への承認に読み替えません。
