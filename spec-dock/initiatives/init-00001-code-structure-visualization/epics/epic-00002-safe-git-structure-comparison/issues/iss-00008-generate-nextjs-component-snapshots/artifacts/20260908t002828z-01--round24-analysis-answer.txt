# Integrated response design

## Smallest coherent response

個別findingごとにRound 24 helperやsurrogate schemaを追加する方法は採用しません。最小responseは、次の一回のauthority-flattening batchです。

### 1. R24-G11のhuman decisionを先に採択する

run provenance、reference inventory、production build inventoryのschema identityとmigration ruleを確定します。

この決定前にactual manifest schemasを変更すると、G02、G06、G08、G10を再度変更する可能性があります。

### 2. Current authorityを一つにする

* Requirement、Design、Planの冒頭current-v1 sectionを唯一のnormative proseとします。
* 後続Round sectionsはhistorical artifactへ移すか、明示的にnon-normativeへ降格します。
* `Round 2 normative closure` 等のpriority文を除去します。
* HTMLはcurrent pre-implementation contractを先頭に示し、historyを折り畳みまたは別artifactへ分離します。
* durable remediation artifactはrepository-relative finding table、digest、exact SHA、session provenanceを保持し、個人absolute pathを正本にしません。

### 3. Surrogate authorityをactual chainへ置換する

実行可能な一本のfixture chainを次の形にします。

```text
frozen package bytes
  -> actual PackageApplicabilityMatrix
  -> actual config/source-plan/source-graph schemas
  -> actual validated adapter request
  -> actual bounded adapter response
  -> actual semantic decision
  -> actual process policy/observation or explicit unobserved
  -> actual final publication decision
  -> actual semantic JSON / PlantUML / domain manifest
     / run manifest / stdout-result / stderr / exit
```

`next-round23-authority-v1`を残す場合は、actual objectsを参照するnon-public test bundleに限定します。別のwire contractやstatus authorityとしては使用しません。

### 4. 修復順序

1. `R24-G10`: canonical authorityとhistoryを整理
2. `R24-G01`: surrogateをactual schemasへ接続
3. `R24-G02`: applicability、4-kind provenance、manifest、run/publication state
4. `R24-G03`: shared config resolver/schema
5. `R24-G04`: frozen source graphとlocality
6. `R24-G05`: process policy/observation

9. `R24-G06`: final decision-only publicationとdiagnostic scope
10. `R24-G09`: finding-level executable registry
11. docs、HTML、durable evidenceを最終actual schemasへ同期

publicationとcoverageを最後にするのは、上流のstate/schema変更を繰り返し投影し直さないためです。

## R24-G11 decision package

### Reproducible condition

同じ `code-structure-viz.next-runtime-manifest/v1` が、run/publication provenanceとexact runtime member/license inventoryの双方を意味しています。actual schemaは後者だけを表します。

### Option A — semantic roleごとにschema familyを分離する

* run/publication provenanceは既存 `run-manifest-v1` と `next-domain-manifest-v1`だけが所有
* checked-in reference fixture inventoryは `next-reference-runtime-inventory/v1`
* future production package inventoryは `next-runtime-build-inventory/v1`
  -現在の曖昧な `next-runtime-manifest/v1` はdeprecated/supersededとして扱う
* current repairでは`pyproject.toml`を変更しない

**Preserved:** single run owner、clear package owner、license attestation、future migration。

**Changed:** schema IDs、existing v1 deprecation policy。

**評価:** 推奨します。run manifestの二重化を避け、reference fixtureとproduction packageを分離できます。

### Option B — current `next-runtime-manifest/v1` をbuild inventoryとして維持する

* actual schemaの現在のroleを維持
* docs冒頭のrun-provenance意味を削除
* run provenanceは既存domain/root manifestだけが所有
* production member変更時に`next-runtime-manifest/v2`を作る
* reference/productionは`kind`ではなくversionまたは別profileで分離

**Preserved:** current schema consumerとの互換性が比較的高い。

**Changed:** current top-level adopted wordingをsupersedeします。

**Risk:** test fixture inventoryとproduction inventoryの語彙が近く、将来再混同する可能性があります。

### Option C — current `next-runtime-manifest/v1` をrun provenanceへrepurposeする

* current top-level wordingを維持
* exact-four inventoryを新しいreference/build schemaへ移す

**Preserved:** current top-level document wording。

**Changed:** actual checked-in schemaの意味を全面的に変更します。

**Risk:**既存 `run-manifest-v1` / `next-domain-manifest-v1` と責務が重複します。

### Rejected option

run provenanceとbuild inventoryを `kind` discriminatorで一つのschema unionにする案は採用しません。一つのIDへ異なるsource of truth、lifecycle、compatibility ruleを残すため、P1-18のroot causeを温存します。

### Recommended decision

**Option Aを推奨します。**

Candidate text — not adopted: `Run and publication provenance SHALL be owned only by code-structure-viz.run-manifest/v1 and the Next domain manifest. Checked-in reference runtime fixtures SHALL use code-structure-viz.next-reference-runtime-inventory/v1. Future shipped adapter, TypeScript, trusted-declaration, and license members SHALL use code-structure-viz.next-runtime-build-inventory/v1 and SHALL be versioned independently from run-state schemas. The ambiguous code-structure-viz.next-runtime-manifest/v1 identifier SHALL be marked superseded and SHALL NOT be used as a second run-state or package-state authority. No pyproject.toml, dependency, lockfile, wheel, or sdist mutation is authorized by this pre-implementation decision.`

### Decision effects

* **Public API:** schema IDsとsupersession metadataが変わります。
* **Data:** production persistent dataは未存在と推定されますが、外部consumer確認が必要です。
* **Security:** measured run factsとstatic package inventoryの混同を除去します。
* **Compatibility:** existing v1のdeprecation/supersession ruleが必要です。
* **Migration:** repository fixtureの移行は必要です。外部consumerが存在する場合は別migration campaignです。
* **Operation:** current production runtimeへ影響しません。
* **Package:** current `pyproject.toml` は変更しません。
* **Rollback:** specification-only commit全体のrevertで戻せます。

同じscope/campaignを継続できる条件は、external consumerとproduction persisted artifactがなく、current repairがschema/docs/tests/fixturesだけに留まることです。それ以外はfresh compatibility campaignが必要です。

# Implementation handoff

**現時点ではimplementation handoffは認可されません。**

理由は、`R24-G11 / P1-18`についてpublic schema identity、source of truth、compatibility、migrationのmaterial decisionが未採択だからです。一意な17 P1修復だけを先行すると、manifest、compatibility、coverage、documentationをG11決定後に再変更することになります。

handoffが成立するためのexact prerequisiteは次のとおりです。

1. `R24-G11`についてOption A、B、Cまたは同等に具体的なcanonical decisionが採択されていること。
2. 採択decisionがschema IDs、existing v1 treatment、run owner、reference inventory owner、production build inventory owner、version/migration ruleを明示すること。
3. external consumerとpersisted artifactの有無が確認されていること。
4. parent workflowが一つのspecification/schema/fixture/reference-test/document repairを明示的に認可すること。
5. handoff作成時にrepository、branch、full tip SHAを再検証すること。
6. affected pathsとsymbolsがそのcurrent SHAで再確認されていること。
7. `src/**`、dependencies、lockfiles、`pyproject.toml`、production adapter、live Node implementationが引き続きnon-goalであること。
8. G01〜G10のFirst Redが再現するか、再現しない項目がdisproof候補として返されていること。

将来のbounded objectiveは一つです。

> Adopted current-v1 authorityをactual private/public schemasと一つのend-to-end reference chainへ投影し、surrogate authorityとhistorical fallbackを除去して、Round 24の18 P1をadditional material choiceなしでsame-reviewer re-review可能にする。

将来のimplementerは、次の場合に停止してparentへ返さなければなりません。

* authority同士の新たな矛盾
* G11 decisionの欠落または曖昧さ
* verified path、symbol、schema、test nodeの不在
* First Redが再現せずfinding前提が反証された
* public API、data、security、privacy、migration、compatibility、rollback、recovery、operation、risk、responsibilityへの予期しない影響
* external consumerまたはpersisted artifactの発見
* production `src/**`変更の必要
* `pyproject.toml`、dependency、lockfile変更の必要
* managed secret、new state store、Windows support、新runtime serviceの必要
* actual OS mechanismを実装しなければreference contractを閉じられない
  -新しいsurrogate schema、dual authority、bidirectional compatibility converterが必要
* complete Unicode profileの導入に新dependencyまたは未採択license/package変更が必要

implementerがparentへ返す証拠は、一つのrepository-relative Markdown remediation recordとし、最低限次を含めます。
