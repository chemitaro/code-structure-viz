先に結論

推奨: Python が Git から source bytes を一度だけ凍結し、その bytes だけを one-shot Node worker に渡します。Node は bundled TypeScript と version/digest/license 固定の TrustedTypeEnvironment で意味解析し、Python が返却 JSON を不信入力として検証してから JSON・PlantUML・manifest を公開します。

設計の中心は「Node を使うか」ではありません。誰が入力と公開結果を信頼するかです。Python core が source acquisition と publication を所有し、Node は閉じた解析 engine に限定します。

安全性

対象 repository の build、config、plugin、package script、application module、node_modules を実行・参照しません。

意味の正しさ

字面の AST scan ではなく TypeChecker と限定的な output-flow を使い、証明できない関係は unknown にします。

diff の安定性

Component 本体と export binding を分け、barrel や alias の変更を Component の消滅・新規作成にしません。

何を作るのか

達成すべき結果は、coding agent が Next.js project の構造を、対象コードを実行せずに比較・追跡できる一つの静的 snapshot として受け取れることです。snapshot には module、component の宣言、公開 export binding、props、静的 relation、client boundary の根拠を含めます。runtime の結果を再現することではなく、証明できた静的事実と証明できない範囲を分離して渡すことが目的です。

そのために static analysis を採用します。TypeScript の AST と TypeChecker から得られる宣言・型・解決結果だけを使えば、build、render、plugin、application module の副作用を起こさずに、同じ入力から同じモデルを作れます。Python が immutable SourceView を一度だけ作ることで、解析中の source drift と再読による非決定性を防ぎます。Node は一回だけ起動する one-shot bridge として frozen bytes を受け取り、解析後に終了します。Node を任意の repository path に接続し続けるより、信頼境界と再現性を小さく保てます。

CLI request → safe source acquisition → TypeScript semantic analysis → validated semantic model → next.snapshot.semantic.json + next.snapshot.puml → run-manifest / stdout / exit code

対象

  • App Router と Pages Router の TS/TSX、safe JS/JSX subset
  • direct export、default export、barrel re-export、alias
  • TypeChecker で得られる effective props signature
  • static import、literal dynamic import、証明可能な JSX render
  • "use client" という正の証拠と、そこから導ける境界 role

対象外

  • Next build、React rendering、RSC Flight、hydration、browser 実行
  • runtime component tree、実行時 conditional branch、custom HOC の一般推論
  • workspace/package manager の自動探索、route selector、temporal diff
  • source snippet、comment、literal default value、secret-like value の出力

全体アーキテクチャと trust boundary

対象 repository の path を Node に渡すと、解析時点の source drift、symlink、package resolution、target node_modules への暗黙依存が増えます。そこで、Python が必要な bytes を先に固定し、Node には virtual filesystem だけを見せます。

責務の境界は明確です。Python core が applicability、freeze、入力検証、ID/count/digest の再計算、JSON・PlantUMLの生成、manifestの公開を所有します。bundled Node/TypeScript は、Pythonから渡された virtual files と trusted declarations の意味抽出だけを所有します。対象 repository の code、build、config、plugin、package script、application module、node_modules、network は、どの層からも実行・参照しません。

projectごとの compiler context

      
複数 project を扱うときは、各 project descriptor が root、source_roots、config_path、compiler_options、所属する file_ids を持ちます。各 file も一つの project_id と roles を持つため、同じ物理 file を複数 project の入力として重複させません。tsconfig.json、jsconfig.json、built-in safe config から得る compiler context は project 単位で凍結し、別 project の設定や target の node_modules を暗黙に混ぜません。

      
一つの path が複数の役割を持つ場合の優先順位も固定します。control > context > program です。control は package/config、context は .d.ts と trusted compiler context、program は解析対象の TS/TSX/JS/JSX を表します。優先順位はroleを捨てるためではなく、同一 record の effective_role と digest を決定するために使います。

      
next.config.*、app/ directory、import の字面、lockfile の間接 entry は applicability evidence にしません。Next project がないと証明できた場合は Node を探さず not_applicable、Next project はあるが Component が 0 件なら complete empty です。

client/server は二値ではない

      
"use client" がないだけで server と断定してはいけません。静的 snapshot では、正の証拠と到達可能性を複数 role として表現します。

      
client_entrydirective prologue に exact "use client" / 'use client' がある直接 fact。

      
client_dependencyclient_entry から internal static value import / re-export で到達可能。

      
server_candidateclosed App Router UI entry seed から client entry の直前まで static value edge で到達可能。runtime server の断定ではありません。

      
unknown上記の正の証拠がない状態。Pages Router も自動 server 扱いしません。

      
BoundaryRolePropagation/v1だけが role の正本です。client entry の seed 自身は client_dependency ではなく、static value closure の target だけがそうなります。client app seed は server_candidate ではなく、server traversal は client entry の直前で止めます。異なる closure の証拠がそろう場合だけ同じ Module の dual role を許します。type-only import、dynamic import、JSX relation、external/unresolved edge は role propagation に使いません。境界 crossing は underlying import edge の boundary_effect facet であり、重複 relation ではありません。Python は facts/router/static value edges から再計算し、submitted model と完全一致させます。

    


    

      
失敗を「安全に成功」に見せない

      
diagnostic があるかどうかではなく、v1 が約束した意味を欠落させたかで結果を分類します。intentional unsupported を unknown として完全に表現できる場合は、diagnostic があっても complete です。


      
partial_safe は独立した証明で決める

      
adapter が「partial」と自己申告しただけでは、payload を公開する根拠になりません。Node response は untrusted input として扱い、Python が全 discovered record、failure root、taint の伝播、causal edge、explicit target witness、collection count を受け取って独立に再計算します。さらに records・roots・closed rule/ownership table から必須 causal edge と taint closure を独立導出し、submitted edge と完全一致させます。frontier は集合として重複を除き、edge omission・shared frontier・boundary role under-taint は拒否します。

      
Python はその証明から安全な subset を一つ作り、JSON と PlantUML の両方へ同じ projection を渡します。したがって、adapter の coverage や status の値だけを転記して成功扱いにはしません。証明材料が不足する、global failureである、または budget を超えた場合は payload_unavailable とし、safe manifestだけを残します。explicit target は canonical key を model から独立解決し、proof の key・status・published ID と一行ずつ完全一致させます。missing、extra、substitution、failed as resolved はすべて拒否します。

schema-driven limits、entity budget、diagnostic、provenance は一つの契約から投影する
