Next.js Component Snapshot
ベストプラクティス設計ガイド

Next.js のコードを実行せず、coding agent が component 構造を安全・決定的に理解するための推奨設計です。実装方法だけでなく、identity、失敗、セキュリティ、Issue #9 の diff への引き継ぎまで一続きで説明します。

先に結論

推奨: Python が Git から source bytes を一度だけ凍結し、その bytes だけを one-shot Node worker に渡します。Node は bundled TypeScript で意味解析し、Python が返却 JSON を不信入力として検証してから JSON・PlantUML・manifest を公開します。

設計の中心は「Node を使うか」ではありません。誰が入力と公開結果を信頼するかです。Python core が source acquisition と publication を所有し、Node は閉じた解析 engine に限定します。

安全性

対象 repository の build、config、plugin、package script、application module、node_modules を実行・参照しません。

意味の正しさ

字面の AST scan ではなく TypeChecker と限定的な output-flow を使い、証明できない関係は unknown にします。

diff の安定性

Component 本体と export binding を分け、barrel や alias の変更を Component の消滅・新規作成にしません。

位置づけ: この資料はゼロベース分析から得た設計候補です。2026-08-31に中心判断が承認され、canonical Requirement / Design / Planへ反映されました。最終authorityはcanonical文書であり、このHTML自体は説明用Artifactです。

何を作るのか

利用者は一つの CLI command で Next.js project の静的 snapshot を取得します。対象は module、component、公開 export、props、静的 relation、client boundary です。

CLI request → safe source acquisition → TypeScript semantic analysis → validated semantic model → next.snapshot.semantic.json + next.snapshot.puml → run-manifest / stdout / exit code

対象

  • App Router と Pages Router の TS/TSX、safe JS/JSX subset
  • direct export、default export、barrel re-export、alias
  • TypeChecker で得られる effective props signature
  • static import、literal dynamic import、証明可能な JSX render
  • "use client" という正の証拠と、そこから導ける境界 role

対象外

  • Next build、React rendering、RSC Flight、hydration、browser 実行
  • runtime component tree、実行時 conditional branch、custom HOC の一般推論
  • workspace/package manager の自動探索、route selector、temporal diff
  • source snippet、comment、literal default value、secret-like value の出力

全体アーキテクチャと trust boundary

対象 repository の path を Node に渡すと、解析時点の source drift、symlink、package resolution、target node_modules への暗黙依存が増えます。そこで、Python が必要な bytes を先に固定し、Node には virtual filesystem だけを見せます。

project をどう選ぶか

      
--repo は引き続き正確な Git root を指します。monorepo 内の Next project は、曖昧な自動探索ではなく --project または config で明示します。

      
code-structure-viz snapshot \
  --repo . \
  --domain next \
  --project apps/web \
  --target component:apps/web/components/index.ts#Button \
  --downstream-depth 2 \
  --output-dir /tmp/next-snapshot

      

        

          
判断推奨 contract理由

          
            
default[next].project_roots=["."]単一 project は追加指定なしで扱える。

            
monorepo--project apps/web を repeatable に指定unrelated package を誤って拾わない。

            
applicableproject root 直下 package.json が dependencies.next または devDependencies.next を直接持つconfig や directory 名を実行・推測しない。

            
shared source[next].source_roots で repository-local path を明示project root 外も opt-in で凍結できる。

            
configtsconfig.json → jsconfig.json → built-in safe config決定的な優先順を持つ。

          
        

      

      
next.config.*、app/ directory、import の字面、lockfile の間接 entry は applicability evidence にしません。Next project がないと証明できた場合は Node を探さず not_applicable、Next project はあるが Component が 0 件なら complete empty です。

    


    

      
identity：Component と export を分ける

      
ここが設計上もっとも重要な判断です。export 名を Component 本体の identity にすると、barrel の移動や alias 変更だけで Component が「削除＋追加」されたように見えます。

      

        推奨: Component は宣言 module と declaration key で識別し、どの module から何という名前で公開されるかは ExportBindingMember として別に表現します。

relation の閉じた vocabulary

      

        

          
relationsource → target成立条件

          
            
static_importModule → Module / externalTypeChecker / resolver で静的 value import を確認。

            
literal_dynamic_importModule → Module / externalspecifier が literal で一意に解決可能。

props を安全に正規化する

      
props は TypeChecker の effective call / construct signature を起点にします。ただし typeToString() や source の型表記をそのまま public contract にすると、compiler version、alias、format、literal value に引きずられます。

      
閉じた type IR

      
primitive、ordinal 化した type_parameter、value を隠した redacted_literals、repository/external reference、array、tuple、union、intersection、parameter name を持たない function、object、opaque だけに正規化します。

      
    
        
  • Unicode NFC、canonical sort、deduplicate、generic parameter の alpha-normalize を行います。
    • 
        
  • children と ref は effective public signature に実在するときだけ出します。
    • 
        
  • default value は出さず、必要なら has_direct_default のような redacted evidence だけにします。
    • 
        
  • 候補上限は depth 16、1 prop 512 nodes、union/intersection 64 members、nested properties 256、component signatures 16 です。
    • 
        
  • 上限到達時は途中で切らず、該当 subtree を opaque(type_complexity_limit) にして coverage を partial にします。
    • 
        
  • any は open-world なので partial。正確な unknown / never は complete にできます。
    • 
      

    


    

      
client/server は二値ではない

      
"use client" がないだけで server と断定してはいけません。静的 snapshot では、正の証拠と到達可能性を複数 role として表現します。

      
client_entrydirective prologue に exact "use client" / 'use client' がある直接 fact。

      
client_dependencyclient_entry から internal static value import / re-export で到達可能。

      
server_candidateclosed App Router UI entry seed から client entry の直前まで static value edge で到達可能。runtime server の断定ではありません。

      
unknown上記の正の証拠がない状態。Pages Router も自動 server 扱いしません。

      
同じ Module が異なる entry context から client_dependency と server_candidate の両方になることを許します。type-only import、dynamic import、JSX relation、external/unresolved edge は role propagation に使いません。境界 crossing は underlying import edge の boundary_effect facet であり、重複 relation ではありません。

    


    

      
失敗を「安全に成功」に見せない

      
diagnostic があるかどうかではなく、v1 が約束した意味を欠落させたかで結果を分類します。intentional unsupported を unknown として完全に表現できる場合は、diagnostic があっても complete です。

公開するファイルと provenance

      

        
next.snapshot.semantic.json
code-structure-viz.semantic/v1 envelope 内の validated semantic facts。

        
next.snapshot.puml
code-structure-viz.plantuml/next/v1 の domain-specific visual vocabulary。

        
run manifest
status、coverage、safe diagnostic、toolchain/config/source-plan version と digest、Artifact SHA-256。

      

      
manifest には Node、TypeScript、adapter、protocol の exact version、project root と config の repository-relative path、source acquisition plan digest、target/depth/budget の requested/resolved 値を残します。source content 自体は残しません。

      
--stdout next:semantic-json のような available selector は、公開 file と完全に同じ bytes を出します。diagnostic は stderr だけです。requested formats は一つの transaction で all-or-none に公開し、既存 path は上書きしません。

    


    

      
process と supply-chain の安全策

      

        

          
risk必須対策

          
            
shell / argument injectionfixed argv、shell=false、fixed adapter entrypoint。

            
target filesystem 読み取りprivate empty cwd、in-memory CompilerHost、request 外 path を解決しない。

            
environment injectionminimal env、NODE_OPTIONS / NODE_PATH を除去。

            
package executionnpm/npx/network/target node_modules/Next config/plugin/script を使わない。

            
resource exhaustionfile/total/stdout/stderr/time/memory cap、process group termination、truncation なし。

            
protocol confusionexact one JSON、closed schema、version check、stdout noise は全 response reject。

            
data leakPython が path/ref/redaction を検証し、raw compiler text や literal を公開しない。

            
supply-chain driftcompiled adapter + exact TypeScript + lockfile + license inventory を一体で bundle。

          
        

      

      
候補上限は 1 file 4 MiB、total 64 MiB、20,000 files、stdout 16 MiB、stderr capture 64 KiB、60 秒、Node old-space 512 MiB です。実測で調整可能ですが、silent truncation と unlimited は不可です。
