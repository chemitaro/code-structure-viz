先に結論

推奨: Python が Git から source bytes を一度だけ凍結し、その bytes だけを one-shot Node worker に渡します。Node は bundled TypeScript と version/digest/license 固定の TrustedTypeEnvironment で意味解析し、Python が返却 JSON を不信入力として検証してから JSON・PlantUML・manifest を公開します。

設計の中心は「Node を使うか」ではありません。誰が入力と公開結果を信頼するかです。Python core が source acquisition と publication を所有し、Node は閉じた解析 engine に限定します。

安全性

対象 repository の build、config、plugin、package script、application module、node_modules を実行・参照しません。

意味の正しさ

字面の AST scan ではなく TypeChecker と限定的な output-flow を使い、証明できない関係は unknown にします。

diff の安定性

Component 本体と export binding を分け、barrel や alias の変更を Component の消滅・新規作成にしません。

位置づけ: この資料はゼロベース分析から得た設計候補です。2026-08-31に中心判断が承認され、canonical Requirement / Design / Planへ反映されました。最終authorityはcanonical文書であり、このHTML自体は説明用Artifactです。
契約の具体化: trusted declarationのshadowing拒否、有限なComponent認定とdefault/export規則、project別config/module resolution、control bytesを再読しないtwo-phase freeze、digest preimage、完全なProps型表現、partial-safeのtaint証明、公開schemaとoffline package contractまで正本で固定しました。Round 6の残存指摘も data-only 契約へ反映しました。後続の差分Issueでは、domain不在だけをempty-sideにし、target解析失敗をadded/removedへ誤変換しません。

何を作るのか

達成すべき結果は、coding agent が Next.js project の構造を、対象コードを実行せずに比較・追跡できる一つの静的 snapshot として受け取れることです。snapshot には module、component の宣言、公開 export binding、props、静的 relation、client boundary の根拠を含めます。runtime の結果を再現することではなく、証明できた静的事実と証明できない範囲を分離して渡すことが目的です。

そのために static analysis を採用します。TypeScript の AST と TypeChecker から得られる宣言・型・解決結果だけを使えば、build、render、plugin、application module の副作用を起こさずに、同じ入力から同じモデルを作れます。Python が immutable SourceView を一度だけ作ることで、解析中の source drift と再読による非決定性を防ぎます。Node は一回だけ起動する one-shot bridge として frozen bytes を受け取り、解析後に終了します。Node を任意の repository path に接続し続けるより、信頼境界と再現性を小さく保てます。

CLI request → safe source acquisition → TypeScript semantic analysis → validated semantic model → next.snapshot.semantic.json + next.snapshot.puml → run-manifest / stdout / exit code

対象

  • App Router と Pages Router の TS/TSX、safe JS/JSX subset
  • direct export、default export、barrel re-export、alias
  • TypeChecker で得られる effective props signature
  • static import、literal dynamic import、証明可能な JSX render
  • "use client" という正の証拠と、そこから導ける境界 role

対象外

  • Next build、React rendering、RSC Flight、hydration、browser 実行
  • runtime component tree、実行時 conditional branch、custom HOC の一般推論
  • workspace/package manager の自動探索、route selector、temporal diff
  • source snippet、comment、literal default value、secret-like value の出力

全体アーキテクチャと trust boundary

対象 repository の path を Node に渡すと、解析時点の source drift、symlink、package resolution、target node_modules への暗黙依存が増えます。そこで、Python が必要な bytes を先に固定し、Node には virtual filesystem だけを見せます。

責務の境界は明確です。Python core が applicability、freeze、入力検証、ID/count/digest の再計算、JSON・PlantUMLの生成、manifestの公開を所有します。bundled Node/TypeScript は、Pythonから渡された virtual files と trusted declarations の意味抽出だけを所有します。対象 repository の code、build、config、plugin、package script、application module、node_modules、network は、どの層からも実行・参照しません。

projectごとの compiler context

      
複数 project を扱うときは、各 project descriptor が root、source_roots、config_path、compiler_options、所属する file_ids を持ちます。各 file も一つの project_id と roles を持つため、同じ物理 file を複数 project の入力として重複させません。tsconfig.json、jsconfig.json、built-in safe config から得る compiler context は project 単位で凍結し、別 project の設定や target の node_modules を暗黙に混ぜません。

      
一つの path が複数の役割を持つ場合の優先順位も固定します。control > context > program です。control は package/config、context は .d.ts と trusted compiler context、program は解析対象の TS/TSX/JS/JSX を表します。優先順位はroleを捨てるためではなく、同一 record の effective_role と digest を決定するために使います。

      
next.config.*、app/ directory、import の字面、lockfile の間接 entry は applicability evidence にしません。Next project がないと証明できた場合は Node を探さず not_applicable、Next project はあるが Component が 0 件なら complete empty です。

閉じたモデルと typed identity

      
公開モデルは、許可した種類だけを持つ閉じたモデルです。Project は入力と provenance のまとまり、Module は物理ファイル、Component は宣言、ExportBinding・ImportBinding・Prop はそれぞれの所有者に属する member です。関係は static_import、literal_dynamic_import、jsx_render、component_wrap の primitive relation に限定します。直接観測した client_entry や router_context は Fact として持ち、導出された role を Fact と偽って追加しません。

      
各IDは「kind + canonical identity tuple」の組み合わせです。したがって、同じ文字列でも Module ID を Component の参照として使うような kind 違いは受理しません。export alias、barrel、re-export は公開場所を表す member を増やすだけで、宣言本体である Component を複製しません。これが alias の変更を Component の削除・追加と誤認しない理由です。

module dependency と component render は別の graph plane にします。Module が Component を所有する関係は zero-hop であり、import relation から全 Component へ暗黙に fan-out しません。

props を安全に正規化する

      
props は TypeChecker の effective call / construct signature を起点にします。ただし typeToString() や source の型表記をそのまま public contract にすると、compiler version、alias、format、literal value に引きずられます。

      
閉じた type IR

      
primitive、ordinal 化した type_parameter、value を隠した redacted_literals、repository/external reference、array、tuple、union、intersection、parameter name を持たない function、object、opaque だけに正規化します。

      
    
        
  • Unicode NFC、canonical sort、deduplicate、generic parameter の alpha-normalize を行います。
    • 
        
  • children と ref は effective public signature に実在するときだけ出します。
    • 
        
  • default value は出さず、必要なら default_evidence = none|parameter_initializer|destructuring_initializer|class_default_props|jsdoc_default のいずれかだけを記録します。値や元の式は保持しません。
    • 
        
  • 候補上限は depth 16、1 prop 512 nodes、union/intersection 64 members、nested properties 256、component signatures 16 です。
    • 
        
  • 上限到達時は途中で切らず、該当 subtree を opaque(type_complexity_limit) にして coverage を partial にします。
    • 
        
  • any は open-world なので partial。正確な unknown / never は complete にできます。

client/server は二値ではない

      
"use client" がないだけで server と断定してはいけません。静的 snapshot では、正の証拠と到達可能性を複数 role として表現します。

      
client_entrydirective prologue に exact "use client" / 'use client' がある直接 fact。

      
client_dependencyclient_entry から internal static value import / re-export で到達可能。

      
server_candidateclosed App Router UI entry seed から client entry の直前まで static value edge で到達可能。runtime server の断定ではありません。

      
unknown上記の正の証拠がない状態。Pages Router も自動 server 扱いしません。

      
同じ Module が異なる entry context から client_dependency と server_candidate の両方になることを許します。type-only import、dynamic import、JSX relation、external/unresolved edge は role propagation に使いません。境界 crossing は underlying import edge の boundary_effect facet であり、重複 relation ではありません。

    


    

      
失敗を「安全に成功」に見せない

      
diagnostic があるかどうかではなく、v1 が約束した意味を欠落させたかで結果を分類します。intentional unsupported を unknown として完全に表現できる場合は、diagnostic があっても complete です。


      
partial_safe は独立した証明で決める

      
adapter が「partial」と自己申告しただけでは、payload を公開する根拠になりません。Node response は untrusted input として扱い、Python が全 discovered record、failure root、taint の伝播、causal edge、explicit target witness、collection count を受け取って独立に再計算します。さらに records・roots・closed rule/ownership table から必須 causal edge と taint closure を独立導出し、submitted edge と完全一致させます。frontier は集合として重複を除き、edge omission・shared frontier・boundary role under-taint は拒否します。

      
Python はその証明から安全な subset を一つ作り、JSON と PlantUML の両方へ同じ projection を渡します。したがって、adapter の coverage や status の値だけを転記して成功扱いにはしません。証明材料が不足する、global failureである、または budget を超えた場合は payload_unavailable とし、safe manifestだけを残します。explicit target は canonical key を model から独立解決し、proof の key・status・published ID と一行ずつ完全一致させます。missing、extra、substitution、failed as resolved はすべて拒否します。

公開するファイルと provenance

      

        
next.snapshot.semantic.json
code-structure-viz.semantic/v1 envelope 内の validated semantic facts。

        
next.snapshot.puml
code-structure-viz.plantuml/next/v1 の domain-specific visual vocabulary。

        
run manifest
status、coverage、safe diagnostic、toolchain/config/source-plan version と digest、Artifact SHA-256。

      

      
manifest には Node、TypeScript、TrustedTypeEnvironment、adapter、protocol の exact version/digest/license、project root と config の repository-relative path、source acquisition plan digest、target/depth/budget の requested/resolved 値を残します。source content 自体は残しません。

      
stdout の selector は、未指定の None（canonical run summary）、manifest（確定した manifest bytes）、next:semantic-json、next:plantuml の四つを固定します。complete、not_applicable、partial_safe、payload_unavailable、fatal、interrupt、usage の全 status について、公開物・exit code・stderr・stdout の exact bytes を matrix で検証します。available selector は公開 file と完全に同じ bytes を出し、unavailable status は typed result、fatal/interrupt は manifestなし、usage は exit 2 かつ空 stdout です。diagnostic は stderr だけで、requested formats は一つの transaction で all-or-none に公開し、既存 path は上書きしません。


      
22個のlimits、diagnostic、provenance は一つの契約から投影する

      
22個の resource limits は request、adapter response、Python validator、run manifest、run fingerprint で別々に定義しません。Python が解決した一つの limits record（file数、file/total bytes、encoded stdin、JSON/string/array、model records、stdout/stderr、timeout、V8 old-space、PropsTypeIR）を全 projection と digest preimageへ伝播します。各上限には対象・計測時点・UTF-8 byteかどうか・境界値を含め、値がちょうど上限なら受理し、1超過時の outcome を固定します。どこか一つだけの上限変更や集計値の改変で、同じ入力の結果が黙って変わらないようにします。

      
diagnostic code の単一 authority は schemas/next-diagnostic-catalog-v1.json です。各 code の severity、recoverability、固定 message、domain、許可する path/symbol reference、outcome を catalog から投影し、adapter の自由文や raw compiler text は公開しません。catalogにない code、誤ったseverity、statusとの不整合は契約違反です。

      
TrustedTypeEnvironment は target package の型を借りる仕組みではなく、bundled declaration と certified symbol の semantic profile です。実際に同梱した declaration bytes と runtime fixture bytes を読み、physical→virtual mapping、size、SHA-256、非循環 inventory attestation、license digest、reserved module/global、certified symbol を known answer と照合します。target側の shadowing、ambient augmentation、path alias、trusted pathとの衝突は fail-closed で拒否します。

      
semantic_compatibility_id は、semantic schema、project と file を含む identity versions、recognition/export/props/relation/fact/boundary algorithm version、trusted semantic profile ID の canonical descriptorから Python が再計算します。source content digestやNodeのpatch versionだけで意味互換性を変えたことにはしません。Issue #9 はこのIDを前提に、Component identityではなく primitive facts、typed members、relation、coverage を差分の入力として使います。domain不在だけを empty-side とし、target解析失敗を added/removed へ変換しません。
