1. 何を分かるようにするのか

AIが「Buttonのpropsを変えると、どこを調べる必要があるか」を判断する場面を考えます。単なるファイル一覧では、別名export、barrel経由の参照、JSXでの利用を区別できません。そこで宣言された実体と、その実体を公開・参照する名前を分けて記録します。

構造を読む

Module、Component、export/import binding、props、静的な関係をJSONとPlantUMLで取得します。

分からない範囲を知る

非リテラルのdynamic importなど、確定できない対象をunknownや診断として残します。

後の比較へつなぐ

同じ宣言には同じIDを与え、別名変更を本体の削除・追加と混同しません。時点間diffはIssue #9の担当です。

対象は明示したNext.js projectのTS/TSXと安全に扱えるJS/JSX、App RouterとPages Routerです。Next build、React描画、RSC Flight、hydrationは実行しません。図が表すのは証明できた静的関係であり、実行時の画面ツリーではありません。

Pythonが必要なバイト列を一度だけ読み、変更できない入力として確定します。Nodeは同梱されたTypeScriptと信頼済みの宣言だけで解析します。Pythonは返却値を検証し、ID・件数・ハッシュを再計算してから公開します。

3. 宣言・公開名・関係を分ける


src/Button.tsxのButtonを、src/index.tsからPrimaryButtonという別名で公開しても、本体は一つです。宣言の所属Moduleとdeclaration keyを本体のIDに使い、公開名はExportBindingMemberへ記録します。



図を描画しています。


図のPlantUMLソース


Componentと認める範囲


exportされた関数・class・許可したwrapperを有限の規則で認定します。匿名default宣言にはmodule内で一つの@anonymous-default slotを使います。任意のHOCや実行時に返る値を推測してComponentへ昇格させません。


propsの表現


propsをprimitive、object、array、tuple、union、intersection、function、referenceなどの閉じた型表現へ変換します。optionalとreadonlyを分け、unionは重複を除いて固定順にします。再帰型・未解決の外部型・制限超過には理由付きopaqueを使います。ソース本文、文字列リテラル、既定値そのものは出力しません。


import/exportの名前


import bindingはnamed / default / namespaceを区別します。import * as UI from "./ui"ではnamespace bindingとUI.Buttonの利用関係を分けます。文字列名exportは構文の観測証拠を保持し、target不達、意図した未対応、export解決失敗を別々に診断します。raw spellingをそのまま公開名へ流しません。

後続実装につながる取得結果の型

SourceDiscoveryIntentは候補名だけです。requestより先にsourceをsealし、CompleteSourceSeal、PartialSourceSeal、SourceAcquisitionUnavailable、SourceIntegrityFatal、SourceProjectUsageのいずれかに確定します。


SourceFailureLedger.from_sealが、同じ凍結入力の依存関係から失敗の影響を導出します。依存先を限定できない呼出しを、依存なしと見なして部分成功にしません。path順序はNFC UTF-8 byte orderです。









5. 静的な関係と、分からない関係を区別する


モジュール間の参照と、Componentの出力に含まれるJSX関係を分けます。importしただけでは、そのComponentを描画したとは限りません。動的構文を見つけたのに無視すると、到達範囲を過小評価してしまいます。



図を描画しています。


図のPlantUMLソース


source graphは凍結bytes、解決済みconfig、projectの所有範囲から導きます。同じimportが二度あれば、二つの出現位置を区別します。位置は文字数でなくUTF-8 byte offsetです。日本語が前に入っても証拠の範囲をずらしません。


解決済みedgeと未解決のopen edgeを分けます。open edgeには安全な相対path・package名、または元bytesの位置に結び付いた不透明な識別子を残します。秘密を含み得るspecifier全文は公開しません。入力から再導出したgraphと比較し、edgeを削除してdigestだけ再計算した偽装を拒否します。


client/server境界とtarget完全性


"use client"は観測した事実です。入口からvalue import等で伝わるclient側の役割を別に計算します。指令がないだけでserver専用とは断定しません。routerの配置やtype-only参照も別の意味として保持します。


選ばれたprogram FileにはModuleがちょうど一つ必要です。指定targetがmissing・duplicate・Component-onlyなら、別のtargetの結果で成功を装いません。proofはtarget、export、件数、参照先がmodelと一致することを検証します。

provenanceはrequest-independentな非該当・失敗と、request-boundな失敗・成功の4種類です。観測行はfieldのschema/versionと実値digestへ結び付けます。未観測の値はunobserved/nullです。既定値を実測値の代わりに入れません。

    4. 

  4. path・ID・参照・proofが同じrequestと矛盾しないか検証する。

  5. 公開modelとproofだけにあるrecordの実数を数える。

--stdoutなしならsummary、manifestならmanifest、next:semantic-jsonやnext:plantumlなら指定artifactのexact bytesを返します。selectorは一度だけ指定でき、要求formatと一致させます。stderrの診断JSONLをstdoutへ混ぜません。

再現性と比較可能性


JSONはNFC・UTF-8・固定key順と改行規則に従います。pathは正規化UTF-8 bytes順、semantic recordはID順です。Unicodeは15.0.0に固定し、hostのUnicode databaseを使いません。日本語や結合文字も公式の正規化テストで検証します。


semantic compatibilityはidentity/algorithm、Unicode、TypeScript、trusted semantic profileの契約を識別します。run fingerprintは実際の入力・設定・制限・toolchainなどを識別します。host固有pathやFDはlocal attestationへ分けます。Issue #9はcompatibilityが一致するsnapshotだけを比較します。
